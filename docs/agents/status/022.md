## Original literal gaps

Deletion contracts and a bounded cleaner were not connected to production Room, C6, startup recovery or a permanent-photo caller. Final removal also needed exact original/request proof and atomic canonical-curation reindexing.

## Implemented behavior and integration

Added durable deletion_requests without a cascading project foreign key, logical DELETING states and bounded no-follow cleanup. Completion receipts survive row deletion. The fixed-revision whole-project API carries the revision shown in the irreversible alert through the repository and atomic Room staging; it cannot reread and adopt a newer revision. It retries only the same whole-project revision and refuses a differently scoped pending photo removal before any unlink. The compatibility delete(id) path retains its existing behavior of finishing prior photo cleanup first. Per-photo deletion verifies original length/SHA and optional 018 request before staging; retry uses durable proof after bytes are removed. Finalization deletes/reindexes canonical and indexed photo positions atomically, advances project/curation revisions once and preserves completed output as stale. The real application command and PhotoRow component now capture project/revision/photo/SHA/bytes/request before an explicit irreversible alert; Cancel performs no mutation and Retry retains the exact confirmation. The service owns its C6 lease. Its own staging changes only project state/message, so the same confirmation remains valid while cleanup is pending. The UI uses the narrow allowPendingPhotoDeletion command allowance; other callers retain their deletion-state checks. The service still validates the exact durable pending request.
