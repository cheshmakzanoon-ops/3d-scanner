## Problem / reproducer

API 33+ notification permission can be first-request, rationale, denied-without-rationale, granted, or disabled in system settings. Treating all false values as a repeated permission request produces misleading UI and may strand a running foreground job without a visible app explanation.

## Required interface

Read facts with `AndroidNotificationPermissionFactsReader.read(...)`, persisting whether the app already requested the runtime permission. Render the pure `NotificationPermissionPolicy.evaluate(facts)` result:

- `REQUEST_PERMISSION`: explain processing visibility, then launch the platform request from user interaction;
- `SHOW_RATIONALE`: show rationale before another request;
- `DENIED_WITHOUT_RATIONALE` / `DISABLED_IN_SYSTEM_SETTINGS`: offer the app notification settings intent;
- `GRANTED` / `NOT_REQUIRED`: no warning.

Never claim that denial stops, completes or fails the reconstruction. The foreground runner must still obey its notification requirement; the UI should explain only that drawer alerts/controls may be unavailable.
