# Agent 018 -> Agent 022: execute staged photo removal safely

- Requesting agent: 018
- Receiving agent: 022
- Immutable source commit: `43640ee198252984b2c4e447607ba207cb24ddda`
- Target: Agent 022 deletion tombstone coordinator and private-file removal worker

## Problem and reproducer
Agent 018 intentionally never deletes files. `RequestRemoval` emits a recoverable `PhotoRemovalDirective.Stage`; treating this as deletion completion would lose originals and break undo/recovery.

## Interface
Consume `Stage(projectId, photoId, photoSha256, request, sourceProjectRevision)` by durably recording a tombstone before any filesystem action. Consume `Cancel` idempotently and preserve/restore the original. Only after durable byte deletion is verified for the same project/photo/request ID and SHA-256 may the owner call `CompleteRemoval` with that exact proof. Duplicate/stale requests must be idempotent or rejected; never infer completion from a missing UI row.

## Minimal adapter pseudocode
`stage -> persist tombstone(PENDING) -> verify current curation request/hash -> delete exact private file -> fsync parent -> mark tombstone DELETED -> execute CompleteRemoval(exact proof)`
On crash before DELETED, recovery reconciles the tombstone and original without fabricating success.

## Tests and verification
Fault injection before/after tombstone write, before/after delete, cancellation/restore races, duplicate request IDs, hash mismatch, process death, and exact completion proof.
