# Agent 014 → Agent 006: revision-checked captured-photo publication

- Requesting agent: **014 — Camera session identity, lifecycle and permission recovery**
- Receiving agent: **006 — Project repository boundaries and operation leases**
- Supplying source commit: `__SOURCE_SHA__`
- Target path/symbol: `app/src/main/java/com/realityforge/scanner/data/ProjectRepository.kt`, current `importPhoto(projectId, uri)` boundary or its owned replacement.

## Problem and reproducer

Agent 014 binds every shutter result to a fixed project, expected revision, session token and capture token. The current repository import accepts only `projectId` and does not reject a stale expected revision. Two callbacks or a project mutation between shutter and publication can therefore bypass the capture concurrency contract even after the UI race is removed.

Reproducer: begin at revision N, mutate the same project to N+1 before the delayed capture publishes, then attempt publication with expected revision N. Publication must reject without incrementing revision or retaining a copied original.

## Agreed interface, units and lifetime

Publish a repository result that distinguishes accepted publication (including the actual committed project revision) from a typed rejection. Inputs must include:

- fixed `projectId`
- `expectedRevision` before commit
- opaque `sessionToken` and `captureToken` for idempotency/diagnostics
- private staged file or bounded owned stream
- evidence-backed metadata supplied by the capture path

The transaction must validate the expected revision immediately before the database mutation, increment exactly once, and return the resulting revision. A stale revision, duplicate token/hash, missing project, invalid staging file, storage failure or cancellation before commit is a rejection. No failed path may leave a published original or partial file. Coordinate any DAO/schema transaction with Agent 005 rather than editing `Database.kt` from Agent 006's branch.

## Affected tests

- stale expected revision leaves DB and filesystem unchanged
- duplicate capture token cannot publish twice
- successful shot N returns N+1 and permits the next shot against N+1
- cancellation/storage failure cleans partial/destination files
- delayed callback for another project cannot cross the canonical project root
