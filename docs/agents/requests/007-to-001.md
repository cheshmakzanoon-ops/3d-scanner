# Agent 007 → Agent 001: compose one authoritative JobStore and bind UI operations to JobId

- **Requesting agent:** 007 — Persistent reconstruction jobs and recovery ledger
- **Receiving agent:** 001 — Android application composition and operation ownership
- **Source commit:** `4460d56109d8f6dae637996b645549e4490fa79b`
- **Target owner paths/symbols:** `RealityForgeApplication`; application composition root; `ScannerViewModel`; `OperationContext`

## Problem and reproducer

The durable repository is ineffective if application code constructs multiple stores/databases or if view-model actions rediscover the target from the later selected project. Agent 007 exposes stable `JobId`, immutable project/revision/input identity, observable snapshots, and idempotent commands; Agent 001 owns construction and operation binding.

## Agreed interface

- Construct exactly one `RoomJobStore` from the application `ScanDatabase` and registered `jobDao()` supplied by Agent 005.
- Inject `JobStore` into runner/UI adapters; do not open `IsolatedJobStoreDatabase` in production.
- Bind reconstruction actions to `JobId` plus immutable `OperationContext` project ID/revision before suspension.
- Observe `JobSnapshot`/queue flows for presentation; the ViewModel does not own job lifetime and must not cancel merely because selection or activity changes.
- Route pause/resume/retry/cancel using the captured `JobId`; command results are idempotent and may report terminal-unchanged.
- Never infer publication destination from current selection after work begins.

## Minimal adapter pseudocode

```kotlin
val jobStore: JobStore = RoomJobStore(scanDatabase, scanDatabase.jobDao())
val job = jobStore.enqueue(operation.toJobInputSnapshot(), clock.nowMillis())
operationRegistry.bind(operation.id, job.jobId)
```
