# Handoff 029 → 008: foreground service and manifest integration

- **Requesting agent:** 029
- **Receiving agent:** 008
- **Source commit:** campaign base `ad3029193f304c70931b94ea7a0df90b69d84b07`; consume the head of `agents/029-processing-notifications`
- **Target paths/symbols:** `app/src/main/AndroidManifest.xml`; Agent 008 durable runner service/command entry point; foreground lifecycle and timeout callback

## Problem / reproducer

The base app has no notification permission, foreground-service permissions/type or processing service, and `MainActivity.onStop()` cancels the ViewModel task. Agent 029 cannot truthfully validate background notification behavior without the execution owner wiring the service and persisted state.

## Required interface

Construct `AndroidProcessingNotificationController` with:

- explicit non-exported command service component;
- `MainActivity` (or Agent 001 deep-link activity) as OPEN component;
- a monochrome small-icon resource;
- durable snapshots supplied by Agent 007.

For every command intent:

```kotlin
val decoded = JobNotificationPendingIntentFactory.decode(
    intent,
    packageName,
    ComponentName(this, ReconstructionService::class.java),
)
val persisted = durableJobs.current(decoded.action.identity.jobId)
val authorization = JobNotificationActionAuthorizer().authorize(decoded.action, persisted)
// mutate only for Allowed and only through the authoritative runner transaction
```

For a RUNNING snapshot, call `controller.build(job)`/`publish(job, facts)` and pass the returned notification to foreground promotion even when the result is `PermissionBlocked`. Do not treat notification permission denial as permission to omit foreground notification creation.

## Minimal manifest/lifecycle adapter

- Declare `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, and the permission associated with the selected processing service type.
- Declare a non-exported foreground service with the correct service type; the current offline local reconstruction should be reviewed against `dataSync` rather than inventing an unrelated type.
- Start from a platform-allowed, user-visible path; promote promptly with the Agent 029 notification.
- On API levels with foreground-service time limits, implement `Service.onTimeout(...)`, stop safely, persist an interrupted/paused state and release native resources.
- Call `restore` after process recreation using only notification-eligible persisted jobs. Cancel orphaned fingerprint-tagged notifications.
- Keep PAUSE/CANCEL bounded and idempotent. RESUME must create a new authoritative runner transition, not trust intent extras.
