## Problem and reproducer
`SparsePipeline.run` currently calls `repository.dao.photos(projectId).take(12)`, so excluded or pending-removal photographs can still enter reconstruction and selected order is ignored. Start a job, exclude/reorder a photo, then let the old job finish: it can publish stale output.

## Interface
Load `PhotoCurationService.selectedPhotos(projectId)`. Call `admitForReconstruction(requiredCount)`; on `Ready`, resolve every ordered `SelectedPhoto.id` to exactly one `ScanPhoto` and verify its SHA-256 equals `SelectedPhoto.sha256`. Carry the returned `ReconstructionSelectionLease` through the job. Do not fall back to timestamp order or `take(12)`.

## Minimal adapter pseudocode
`selection = curation.selectedPhotos(id) ?: fail`
`lease = (selection.admitForReconstruction(profileMinimum) as Ready).lease`
`photos = lease.orderedPhotoIds.map { dao.photoById(id, it) }.also { verify hashes/order }`
Before handing artifacts to publication, reload the selected set and require `ReconstructionSelectionGuard.verifyPublication(lease, current) is Current`.

## Tests and verification
Add engine tests proving excluded/pending photos are absent, selected order is stable, hash mismatch fails closed, custom minimum admission is honored, and a selection change during execution prevents publication.
