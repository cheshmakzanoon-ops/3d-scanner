# Agent 018 contract: photo curation and reconstruction selection

Contract version: `photo-curation-v1`

Owner: Agent 018 (`agents/018-photo-curation`)

## Purpose

This package provides revision-safe commands for including, excluding, ordering, staging permanent removal, restoring staged removal, completing a verified deletion, and immediately undoing reversible curation changes. It never reads, writes, renames, or deletes photograph files. Original bytes remain owned by the repository/deletion services.

Production API: `app/src/main/java/com/realityforge/scanner/data/curation/`

- `PhotoCurationService.state(projectId)` returns ordered photo status for Agent 073.
- `PhotoCurationService.selectedPhotos(projectId)` returns the immutable reconstruction input contract for Agent 002.
- `PhotoCurationService.execute(command)` performs one expected-revision command.
- `PhotoCurationStore` is the transactional persistence port implemented through Agents 005/006.
- `ReconstructionSelectionGuard.verifyPublication` rejects publication by a job whose selected input identity is no longer current.

## Identity and ordering

Each curated photo has a stable photo ID, immutable lowercase SHA-256 of the original, and a contiguous zero-based position. A `SelectedPhotoSet` contains only `INCLUDED` photos, preserves their relative order, and compacts selected positions to `0..n-1`. Its SHA-256 fingerprint is length-delimited and includes project ID, selected photo IDs, original hashes, and selected order.

The defensive metadata limit is 4,096 photos. This is only a parser/allocation bound; it does not qualify a 4,096-photo reconstruction profile.

## Revisions

`CurationRevision` has two monotonic values:

- `projectRevision` changes only when reconstruction inputs or the retained original set change: include/exclude, selected-order change, removal staging/restoration, or verified removal completion.
- `curationVersion` changes for every applied metadata mutation, including a reason-only update or movement of excluded photos.
- A no-op command commits nothing and changes neither value.

All commands carry the latest expected pair. A store commit must compare both values and atomically persist the next photo metadata, revision, and invalidation decision. A stale command returns `RevisionConflict` and cannot partially apply.

## Curation states

- `INCLUDED`: contributes to reconstruction.
- `EXCLUDED`: original remains retained; a typed reason is stored; it does not contribute.
- `REMOVAL_PENDING`: original still exists and is counted as retained, but it does not contribute. The exact removal request ID, original SHA-256, previous state, reason, and timestamp are retained for recovery/restore.

Exclusion is never deletion. `RequestRemoval` only emits `PhotoRemovalDirective.Stage` for Agent 022. `RestorePendingRemoval` or undo emits `PhotoRemovalDirective.Cancel`. `CompleteRemoval` is accepted only when the staged request ID and original SHA-256 exactly match the durable deletion completion supplied by Agent 022. It compacts metadata after deletion and intentionally has no undo token.

## Reconstruction admission and publication

`SelectedPhotoSet.admitForReconstruction(requiredCount)` produces a fixed `ReconstructionSelectionLease` containing project ID, project revision, selected-input fingerprint, and ordered photo IDs. Before publication, Agent 002/023 must load the current selected set and call `ReconstructionSelectionGuard.verifyPublication`. Any project, revision, fingerprint, or order mismatch is `Stale`; partial output must not become current.

Reason-only metadata changes do not stale a reconstruction because neither the selected input nor project revision changes. Include/exclude/reorder/removal changes do.

## Undo

Applied reversible commands return an opaque `CurationUndoToken`. Undo is accepted only when:

1. project identity matches;
2. the current complete revision equals the token's post-command revision; and
3. the complete curation-state fingerprint still equals the token's post-command fingerprint.

Undo creates a new monotonic revision; it never rewinds revision counters. An intervening mutation makes an older token inapplicable. A completed permanent deletion is not undoable.

## Required store transaction

For `CurationCommitRequest`, the adapter must in one transaction:

1. compare project ID and both expected revision values;
2. persist all ordered curation rows/fields in `nextSnapshot`;
3. update the project revision values;
4. invalidate or stale active/current artifacts when `change.projectRevisionChanged` is true;
5. retain the previous completed result according to Agent 023's publication contract; and
6. return the exact committed snapshot.

The adapter must not infer ordering from timestamps, array position outside the stored position field, display names, or mutable UI selection.

## Failure and cancellation behavior

Invalid identities, permutations, stale revisions, mismatched deletion proof, missing photos, and inapplicable undo are typed rejections. Store read/commit failures become `StoreFailure`. Coroutine cancellation is rethrown and is never converted to a recoverable command failure.
