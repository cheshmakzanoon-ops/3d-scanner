# Actual UI journey and evidence contract

`uiflow.ActualUiJourneyTest` uses actual MainActivity controls, Android accessibility
actions and DocumentsUI for create/import/reconstruction/studio/export/reopen.
Controller calls are confined to independent outcome/hash assertions and cleanup,
not the actions under test. Synthetic relief JPEGs are explicitly labelled and
materialized through MediaStore Downloads; screenshots come from UiAutomation.
The simple journey covers dialog cancellation/rotation/reopen; the complete journey
requires real available photographic output and fails rather than replacing it with
a stock model. `CameraPermissionJourneyTest` requires denied permission established
outside the target process and drives denial/regrant through actual system controls.
It does not label a virtual-camera image as physical capture.

`InterruptionUiJourneyTest` consumes actual001 C1 pending-request state for
read-only identity assertions while mutations remain actual screen/picker actions.
It cancels a real picker, recreates the initiating Activity with DocumentsUI still
foreground, checks the same UUID/project/revision, repeats the normal088 fixture
without a duplicate revision, and imports a distinct synthetic input. A second
test project remains unchanged. Its HOME/return/recreate/reopen journey preserves
the exact originals/revision; this is not a process-death or lock/reconnect claim.

Its distinct nonsecure lock/wake test requires an awake unlocked fixture without
credentials, executes GLOBAL_ACTION_LOCK_SCREEN, observes actual locked plus
noninteractive state, and wakes/dismisses only that nonsecure keyguard through
external shell commands. It observes unlocked/interactive state and the same
project/revision/original hashes afterward. This supplies UI-state lock coverage;
008/088 interrupted-job reconnect and true process recovery remain separate gates.

Permission denial/regrant now has a direct instrumentation runner row. Host-only
`pm revoke` and permission-flag reset run before instrumentation, retain logs and
fail closed. Neither permission revocation nor process control is implemented
inside the target process. The physical row invokes the owned
`PhysicalCaptureJourneyTest`, requires identified real hardware and authorized
nonprivate scene args, and proves actual CameraX JPEG publication/hash preservation
after reopen. Its bounded terminal metadata is checked independently by the host.
It never seeds a photograph or exports the captured JPEG; only the safe library
success screenshot is retained. Hardware/runtime execution remains a separate gate.

The executable Python runner in `tools/android-ui-e2e` verifies exact source/APK/
test-APK provenance, device identity and underlying instrumentation test counts,
rejecting zero-test/skip/stale evidence. It supports an explicit adb executable,
including a container-hosted adb client when the cloud user's home is read-only.
Each run has a unique screenshot prefix so old screenshots cannot stand in for a
current run. No localhost preview or uploaded photo is involved.

Process termination and provider faults belong to088 shared external controller /
fault provider.080 supplies named UI scenarios and consumes that controller; it
does not implement a duplicate in-process kill or production manifest provider.
Missing088 delivery leaves those gates BLOCKED_EXTERNAL/NOT_RUN. Physical-camera
entrypoints require actual hardware identity and explicit operator evidence;
emulator synthetic tests cannot satisfy physical optics or performance gates.

Run the documented runner against compiled app/test APKs and a build receipt
recording source SHA and hashes. Keep executed/passed/failed/skipped/unrun distinct.
Final candidate qualification must include all product owners, not only this suite.
