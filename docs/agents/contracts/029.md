# Agent 029 contract — processing notifications

## Owned API

Package: `com.realityforge.scanner.processing.notifications`

- `ProcessingJobIdentity(projectId, jobId, operationId, sourceRevision)` is the complete immutable key for one durable processing attempt. Every notification tag, id, request code, intent URI and action payload derives from all four fields. IDs supplied by persistence must be opaque identifiers, not user-visible names or filesystem paths.
- `PersistedProcessingJob` is the privacy-minimized input snapshot. It carries status, optional named stage, stage-local progress, action availability and timestamps. It intentionally carries no thumbnail, project title, error detail or path.
- `ProcessingNotificationMapper` maps persisted truth to queued/running/paused/failed/completed presentation. Unknown work remains indeterminate; known counts are explicitly confined to the current stage.
- `JobNotificationPendingIntentFactory` creates explicit immutable intents. The URI contains only an action and SHA-256 identity digest; package, expected component and payload identity are revalidated while decoding.
- `JobNotificationActionAuthorizer` must run after decoding and after loading the current job from authoritative persistence. Identity and current-state checks reject stale notifications, replaced operations and cross-project commands.
- `ProcessingNotificationController` creates channels, builds/posts/removes notifications and reconciles app-owned notifications from restore-eligible persisted snapshots. Its Android implementation uses private lock-screen visibility plus a generic public version and fingerprint-based notification tags.
- `NotificationPermissionPolicy` is the UI/service-neutral decision model for API 33+ runtime permission, rationale and settings recovery. A denied drawer permission never removes the platform requirement for an active foreground service to supply a notification object.

## Integration sequence

1. Agent 007 loads a current durable job snapshot and converts it to `PersistedProcessingJob`.
2. Agent 008 constructs `AndroidProcessingNotificationController`, creates channels, and calls `publish` on each durable state transition. On process creation it calls `restore` with only jobs that persistence declares notification-eligible.
3. For RUNNING, Agent 008 passes `BuiltProcessingNotification.notification`, tag and id to the foreground-service lifecycle. `PermissionBlocked` still returns the required notification object.
4. The explicit command component decodes the intent, reloads the current job, calls `JobNotificationActionAuthorizer`, and only then delegates pause/resume/cancel to the durable runner.
5. OPEN is routed through Agent 001 to the matching current project/job view. Stale identities are not silently rebound to another operation.
6. Agent 074 renders `NotificationPermissionDecision` and persists whether the runtime prompt was already requested. Permission changes must call `publish(..., force = true)` or restore; the controller also detects changed permission states.

## Platform and privacy constraints

- The service/manifest owner must declare the correct foreground-service type and permissions, start only from platform-allowed/user-visible paths, call foreground promotion promptly, and implement current timeout handling.
- Notifications never include private photos, thumbnails, names, filesystem paths, raw failure strings, fabricated whole-job percentages or invented time remaining.
- The notification data URI carries a version, action and digest. The full typed identity remains in an explicit app-only intent and is never trusted without persisted-state authorization.
- Notification channel IDs are stable: `rf_processing` and `rf_processing_results`. Channel importance is not programmatically escalated after user choice.
- The result of `build` is deterministic from a persisted snapshot; publication and service lifecycle remain separate so permission denial cannot be mistaken for job failure.
