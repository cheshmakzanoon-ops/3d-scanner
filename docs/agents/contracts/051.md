# 051 scoped native work evidence

`cancellation::Scope(shared_ptr<const atomic_bool>)` leases the cancellation flag
for the native call; existing synchronous raw-pointer Scope remains compatible.
Nested scopes restore their caller and each execution thread has independent state.
No registry or handle is invented: owner003 must bind its actual leased token.

`progress.hpp` is header-only. `rf::progress::Scope(shared_ptr<State>)` owns the
pullable, mutex-protected latest Snapshot. `begin(Stage, reference, tile, total)`
and `advance(completed)` check cancellation before publishing bounded local work.
Unknown totals are null; counts must be monotonic inside one stage/tile. There
is no percentage, callback, pixel event queue, Java pointer or asynchronous work.
Producer calls belong at bounded iterations/rows/tiles, not per pixel. Polling
cadence belongs to002/003; scope destruction releases the state and restores an
outer scope. Stage changes reset counters explicitly through begin.

Example kernel loop: `progress::begin(Stage::Depth, reference, tile, rows);`
then each bounded row `progress::advance(row + 1)`. Never catch Cancelled as a
quality warning. The bridge must discard temporary outputs on cancellation.


## Unfinished HOST per-kernel timing plan saved at user stop

No new timing harness source was authored, compiled or executed. The existing
progress test measures only a generic ten-million-advance loop. Actual PnP,
dense and texture tests prove interruption, but representative per-kernel
worst observed cancellation-return latency remains unmeasured. This is a
feasible HOST evidence gap, separate from physical Android qualification.

The approved but unfinished plan was an owned C++ probe plus a Python driver
with explicit source-root, immutable source commit and native-library hash. It
would compile against those exact public headers and reuse existing synthetic
PnP, dense and atlas fixtures. Each worker would install leased cancellation
and progress scopes. Cancellation would follow an observed active-kernel
progress barrier, with completed work strictly above zero and the operation
still active; a sleep alone would not establish entry. The intended receipt
would record each trial, active snapshot, failures, fixture bytes/hashes,
source/library hashes and worst observed cancellation-return latency for each
kernel. Operational timeouts would be distinguished from performance limits;
no flaky fixed latency gate or physical-device claim was planned. CPU usage
was limited to one extra CPU while emulator validation was active.

Development stopped before implementation at the user's explicit instruction.
This saved plan is not executable code or passing measurement evidence.
