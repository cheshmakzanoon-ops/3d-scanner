## Immutable capture identity

`CaptureSessionIdentity(projectId, initialRevision, sessionToken)` is created before opening the
camera. The project and token never change during that camera route. `CapturedPhoto` repeats the
project ID, expected project revision, session token and per-shot token; no publication path may
look up a replacement destination from mutable UI selection.

Each accepted photo transaction returns `CaptureCommitOutcome.Accepted(committedRevision)`. The
controller uses that committed revision as the next shot's expected revision while retaining the
same session token. Rejection keeps the current expected revision and removes the private staging
file. A non-advancing accepted revision is treated as an invalid publication response and cleaned.

## File ownership and callback lifetime

1. `CaptureStagingStore` creates hashed session/shot paths only below
   `cacheDir/capture-staging-v1`.
2. CameraX writes the file while the session controller owns it.
3. `onImageSaved` either rejects/deletes a stale callback or transfers a `CapturedPhoto` to the
   publication owner.
4. On `Accepted`, the publication owner owns final cleanup of the staging file after importing it.
   On `Rejected`, Agent 014 deletes the staging file.
5. Closing a route does not race-delete a file CameraX may still be writing. The eventual callback
   is rejected and removes it. A later session prunes only age-qualified abandoned directories;
   merely observing a different token is never treated as proof that an old writer has stopped.

Duplicate callbacks never delete a file already being read by the publication owner. Camera errors
remove only the matching undelivered attempt. A capture from a closed/replaced controller cannot
modify the state of a new controller.

## Lifecycle and permission behavior

`CaptureSessionState` distinguishes waiting, binding, ready, capturing, committing, paused,
unavailable and closed. System Back is handled inside the screen even during capture. CameraX use
cases are bound to the route's lifecycle and only those exact use cases are unbound on disposal.
Rotation is updated from configuration and orientation observations. Save count and next expected
revision are restored through `rememberSaveable`; an in-flight shot is not presented as committed
after recreation.

`CameraPermissionPolicy` maps observable Android facts to granted, first-request, rationale,
permanent-denial/settings and camera-unavailable states. Permission is rechecked on resume so a
settings grant or runtime revocation updates the route. Every non-camera state explicitly retains
photo-import access.

## Extension seam

`CaptureSessionExtension` is the sole Agent 014 camera-binding seam for Agents 015–017. Extensions
may supply session-scoped CameraX `UseCase` objects and receive `onCameraBound` /
`onCameraUnbound`; they must not independently bind/unbind the provider. User-facing extension
content is passed through the `sessionContent` slot with the current `CaptureSessionState`.
