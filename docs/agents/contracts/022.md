# Agent 022 contract — recoverable deletion

## Scope

Agent 022 owns the deletion protocol and private-file cleanup implementation under
`com.realityforge.scanner.data.deletion`. It does not own Room entities/DAOs, the repository
facade, job scheduling, result publication, cache retention, or UI composition. Those owners
consume this contract rather than reimplementing recursive deletion.

Deletion means explicit permanent removal. Photo exclusion/curation is a reversible selection
operation and must never create a deletion tombstone or remove an original.

## Public protocol

- `DeletionIntent` is non-destructive. Only `DeletionIntent.confirm(...)` creates a
  `ConfirmedDeletionRequest`, which is the only request accepted by `DeletionService`.
- `PendingDeletion` is the durable, UI-presentable state. Its operation, scope, expected
  revision, confirmation time, immutable target snapshot, retained-reference identities,
  counters, blockers, and failure survive process death.
- `DeletionPersistence` is implemented by Agent 005. `stageConfirmed` atomically validates the
  expected project revision, records the tombstone/targets, and logically marks the project or
  photo deleting so no new operation can start.
- `DeletionLeaseCoordinator` is implemented through Agents 006/007. It drains admitted work and
  identifies typed blockers; logical deletion remains in force after the cleanup lease releases.
- `PrivateFileCleaner` removes only `OwnedDeletionTarget` values captured in the tombstone. It
  uses bounded, cancellable, idempotent, no-follow traversal and reports measured entries/bytes.
- `DeletionService.confirmAndRun`, `retry`, and `recoverPending` preserve this ordering:
  tombstone -> lease/drain -> bounded file cleanup -> files-removed proof -> atomic DB finalization.

## Durable phases and crash meaning

1. `TOMBSTONED`: logical deletion and immutable owned-target snapshot committed.
2. `WAITING_FOR_ACTIVITY`: current import/capture/reconstruction/export/curation/cache/publication
   work still owns the target. New work remains blocked.
3. `CLEANUP_PENDING`: one bounded pass committed progress and another pass is required.
4. `CLEANING_FILES`: a cleanup attempt holds the deletion lease. A process death here causes a
   safe re-enumeration; already missing paths are idempotent success.
5. `RETRYABLE_FAILURE`: typed cleanup failure and measured partial progress are retained for UI.
6. `FILES_REMOVED`: every staged target is absent. This is the only phase allowed to advance to
   DB finalization.
7. `FINALIZING_DATABASE`: row/reference finalization may be retried idempotently.
8. `COMPLETED`: file cleanup and the final database transaction both committed.

`DeletionStateReducer` is the normative transition/counter implementation. Persistence adapters
must use equivalent compare-and-set semantics on `stateVersion`; impossible phase skips fail.

## Path and reference rules

- Tombstones persist no absolute path. Targets are canonical project UUIDs plus validated `/`
  separated project-relative paths.
- A photo tombstone cannot contain `ProjectTree`.
- The persistence/publication owners must snapshot only app-private paths exclusively owned by
  the deleted scope. Still-shared paths are omitted and represented by `retainedReferenceIds`.
- Whole-project `ProjectTree` is valid only when every path below that project directory is
  exclusive to the project. Duplication must use independent files or an explicit reference
  inventory; filename guessing is not sufficient.
- Intermediate symlinks are rejected. A final symlink is unlinked without following it.
  Traversal revalidates parents immediately before deletion and cannot leave the staged tree.
- External source photographs/document-provider files are never deletion targets.

## Persistence atomicity required from Agent 005

`stageConfirmed` is one transaction. For the same operation ID it is idempotent only when scope,
revision, confirmation version, and immutable targets match; a conflicting replay is rejected.
The tombstone must remain independently readable after project/photo rows are finalized.

`transition` is a state-version CAS. `finalizeDeletion` accepts only
`FINALIZING_DATABASE`, atomically removes the intended rows/references, advances the tombstone to
`COMPLETED`, and never cascades away the completion receipt. Startup queries return all
non-completed tombstones in stable bounded order.

## UI behavior

Before confirmation, cancel/dismiss performs no durable write. After confirmation, the target is
shown as deleting/pending cleanup rather than silently disappearing. UI maps typed blockers and
failures to localized copy, exposes retry, and reports completion only for `COMPLETED`. If cleanup
failed, remaining private data stays represented by the tombstone even if ordinary project work
is disabled.

## Verification supplied by Agent 022

The JVM suite covers explicit confirmation, bounded multi-pass cleanup, active-operation waiting,
retryable failure, cancellation, retained/shared targets, symlink/traversal defense, unrelated
projects/external photos, and simulated process death at six DB/file boundaries. Android
instrumentation exercises the real app-private filesystem and symlink behavior. Integrated Room,
facade, startup, and UI tests remain the receiving owners' merge gates.
