# Agent 005 — durable database contract

Status: schema version 2 implementation contract for integration from `agents/005-database-migrations`.

## Compatibility boundary

- Version 1 is the immutable migration baseline. Its exported Room schema is checked in at `app/schemas/com.realityforge.scanner.data.ScanDatabase/1.json`.
- Version 2 is additive. It preserves every version-1 project row, original-photo metadata/hash, revision, state/message, `resultRevision`, and `resultKey`.
- The application continues to open `realityforge.db` through the existing `Room.databaseBuilder` call. `ScanDatabase` declares the 1→2 auto-migration, so no destructive fallback or caller-owned migration registration is permitted.
- Project `state` remains a text machine code solely for version-1 source compatibility. UI copy must come from `message` or presentation code, never by displaying raw state codes.

## Version-2 tables and identities

### Existing tables

`projects`

- Stable primary key: `id`.
- Revision is monotonic. Any photo/curation mutation invalidates prior results by incrementing `revision` and clearing `resultRevision`/`resultKey`.
- New indices: `revision`, `state`.

`photos`

- Stable primary key: `id`; project FK cascades on project deletion.
- Existing per-project content identity remains unique: `(projectId, sha256)`.
- New curation fields: `included`, `selectionOrder`.
- New capture binding: nullable `captureSessionId` FK and nullable `captureSequence`; `(captureSessionId, captureSequence)` is unique.
- `ScanDao.addCapturedPhoto` is the supported capture insertion primitive. It requires an open session owned by the same project, then inserts and invalidates the project in one transaction.

### New tables

`capture_sessions`

- Primary key `id`; unique `(projectId, identitySha256)` idempotency identity.
- Bound to `projectId` and `sourceRevision` at creation.
- Camera/lens identities are hashes, not mutable display names.

`reconstruction_jobs`

- Primary key `id`; unique `(projectId, identitySha256)` prevents duplicate logical jobs.
- `inputRevision` is immutable. A job may be created only when it equals the current project revision.
- `attempt` is a monotonic compare-and-set epoch. Every successful acquisition increments it.
- `leaseToken` is globally unique while present. Lease owner, token, attempt, and expiry must all match for renewal, pause, completion, or failure publication.

`artifacts`

- Primary key `id`; unique per-project `identitySha256` and `relativePath`.
- Stores immutable project revision, representation/kind codes, byte size, path, and content hash.
- A job reference is constrained to a job in the same project by a composite FK.
- Artifacts are inserted pending and become visible as completed outputs only after `commitArtifact`; commit is rejected when the project revision has moved.

`edit_recipes`

- Primary key `id`; unique `(projectId, identitySha256)`.
- Parent artifact is constrained to the same project by a composite FK.
- `operationsJson` is an immutable, versioned recipe payload. Agents owning edit semantics own its JSON schema; Agent 005 owns only storage columns and relational integrity.

`deletion_journals`

- Primary key `id`; exactly one row per `projectId`.
- Deliberately has no project FK so recovery survives deletion of the project row.
- Stores expected revision, project-root relative path, compare-and-set attempt, phase, update time, and last error code.

## Stable state codes

Project lifecycle text codes retained for version-1 compatibility:

- `NEW`, `READY`, `PROCESSING`, `INTERRUPTED`, `FAILED`, `SPARSE_READY`.

Capture session integer codes:

- `0 OPEN`, `1 CLOSED`, `2 CANCELLED`.
- Only `OPEN→CLOSED` and `OPEN→CANCELLED` are legal.

Reconstruction job integer codes:

- `0 QUEUED`, `1 RUNNING`, `2 PAUSED`, `3 COMPLETED`, `4 FAILED`, `5 CANCELLED`, `6 STALE`, `7 BLOCKED_EXTERNAL`.
- Acquisition accepts `QUEUED`, `PAUSED`, or an expired `RUNNING` lease and increments `attempt`.
- A cancellation request blocks new acquisition and completion.
- Completion requires a live matching lease, current project revision, and a committed artifact for the same project/job/revision.
- Failure publication accepts only terminal codes 4–7 and requires the live matching attempt/token.

Deletion phase integer codes:

- `0 PLANNED`, `1 FILES_REMOVING`, `2 FILES_REMOVED`, `3 DATABASE_REMOVED`, `4 COMPLETED`, `5 FAILED_RETRYABLE`.
- Legal progress is `0→1→2→3→4`; phases 0–3 may move to 5; retry is `5→1`.
- Every phase change is compare-and-set on both phase and attempt. `COMPLETED` is terminal.

## Transaction primitives

Return value convention for guarded mutations: `1`/`true` means this caller committed the transition; `0`/`false` means stale, duplicate, illegal, cancelled, or otherwise non-owning. Callers must not infer success from intent.

- `ScanDao.curatePhoto`: photo update plus project revision invalidation, atomically.
- `ScanDao.addCapturedPhoto`: capture-project validation, photo insert, and revision invalidation, atomically.
- `DurableStateDao.createCaptureSessionForCurrentRevision`.
- `DurableStateDao.createJobForCurrentRevision`.
- `DurableStateDao.tryAcquireJob`, `renewJobLease`, `pauseJob`, `completeJob`, `finishJobWithFailure`.
- `DurableStateDao.createPendingArtifactForCurrentRevision`, then `commitArtifact` only after filesystem publication has been durably completed by the storage owner.
- `DurableStateDao.beginDeletionForCurrentRevision`, then `advanceDeletion` after each idempotent storage/database step.

The low-level DAO does not claim a filesystem path exists. Storage owners must validate content hashes and surface missing/corrupt artifacts; they must never silently recreate or relabel missing output as committed.

## Migration behavior

The Room-generated 1→2 DDL runs transactionally with `ScanDatabaseV1ToV2.onPostMigrate`.

- Legacy photos receive deterministic `selectionOrder` by `(addedAt, id)` within each project.
- New capture fields remain null for legacy photos and `included` defaults to true.
- A post-migration `PRAGMA foreign_key_check` fails the migration rather than publishing inconsistent state.
- Checked-in schemas are compiler output, not hand-authored approximations.
- Real on-disk instrumentation fixtures cover row/hash/result preservation, restart, interrupted transaction rollback, exact schema validation, foreign keys, lease recovery, duplicate identities, stale attempts, and deletion idempotency.

## Integration ownership

- Agent 005 owns schema/table/column/index names, schema version increments, migration specs, and database-level transition primitives.
- Agents 007, 013, 018, 022, 023, and 066 consume this contract for job services, capture, artifact publication, curation, edit persistence, and deletion recovery. They must not independently rename columns, change code values, or increment the Room version.
- Agent 004 must package `app/schemas` as Android-test assets (or adopt the Room Gradle plugin equivalently) so `MigrationTestHelper` can execute the checked-in migration fixtures.
- Agent 100 resolves any integration-time schema change through a new Agent-005-compatible migration; never use destructive migration fallback.
