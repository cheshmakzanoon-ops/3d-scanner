# Agent 009 contract: artifact identity, manifests, and alignment checkpoints

## Scope

This contract defines C8 for offline reconstruction artifacts. It deliberately separates:

1. **content identity** — which exact inputs, algorithms, settings, coordinate convention, and accepted parent stages produced a stage;
2. **job ownership** — project ID, source revision, job ID, and monotonic attempt that may reuse or publish it; and
3. **quality acceptance** — independent structural, geometry, appearance, or interoperability evidence.

A SHA-256 match proves byte integrity only. It does not prove that cameras are valid, geometry is acceptable, a texture is supported by photographs, or an export is interoperable.

## Production API

All new types are under `com.realityforge.scanner.engine.artifacts`.

- `InputSnapshot` / `InputSnapshotCodec` — ordered included photographs, original-byte hash, capture-metadata hash, dimensions, calibration hash, coordinate-convention identifier, engine-compatibility identifier, and exact `ArtifactBinding`.
- `ArtifactIdentityPolicy.build(...)` — canonical identities for `FEATURES`, `MATCHES`, `ALIGNMENT`, `DENSE_DEPTH`, `SURFACE`, `TEXTURE`, `LOD`, and `EXPORT`.
- `StageIdentity` — algorithm ID/version/implementation hash, canonical settings, relevant input-component hashes, and accepted parent identities.
- `ArtifactRef` / `StageManifest` / `StageManifestCodec` — representation, media type, byte size, SHA-256, completion state, exact dependencies, and independent acceptance evidence.
- `StageManifestValidator.validateForReuse(...)` — checks binding, snapshot, stage identity, parent manifest hashes, parent completion, required artifact sizes/hashes, and acceptance kind.
- `ArtifactIntegrity.probe(...)` — bounded streaming SHA-256 over a regular private file; rejects traversal and symbolic artifact paths.
- `AlignmentCheckpoint` / `AlignmentCheckpointCodec` — accepted cameras, verified match graph, stable sparse tracks, observations, colour, and residual evidence.
- `AlignmentCheckpointValidator.validateForReuse(...)` — additionally validates intrinsics, proper orthonormal world-to-camera rotations, non-zero baseline, connected accepted match graph, observation indices, finite bounded points, and residual gates.
- `AlignmentCheckpointComparator.compare(...)` — verifies restored camera/sparse geometry against the uncached accepted result with declared numerical tolerances.

All aggregate constructors defensively copy lists, maps, and sets before hashes can be memoized.

## Wire formats and hard bounds

Every format uses a four-byte ASCII magic, big-endian wire version, bounded payload length, payload SHA-256, then canonical payload bytes. Unknown wire/schema versions, trailing bytes, malformed UTF-8, impossible counts, non-finite numbers, and payload/hash mismatches are rejected.

| Record | Magic | Wire/schema | Maximum payload | Principal bounds |
|---|---|---:|---:|---|
| Input snapshot | `RFSN` | 1 / 1 | 2 MiB | 4,096 ordered photos |
| Stage manifest | `RFSM` | 1 / 1 | 1 MiB | 256 artifacts; at most one dependency per stage |
| Sparse alignment | `RFAC` | 1 / 1 | 128 MiB | 4,096 cameras; 250,000 verified edges; 1,000,000 tracks; 8,000,000 observations |

Artifact paths are project-relative, `/` separated, traversal-free, and non-symbolic when probed. A complete artifact must be non-empty. A complete stage must contain at least one required artifact and accepted evidence of the stage-appropriate kind.

## Canonical invalidation policy

The table lists direct identity inputs. Parent identities propagate invalidation to descendants.

| Stage | Direct inputs | Accepted parent(s) |
|---|---|---|
| Features | ordered included photo bytes/metadata; engine compatibility; feature algorithm/settings | none |
| Matches | engine compatibility; matching algorithm/settings | Features |
| Alignment | calibration; coordinate convention; engine compatibility; alignment algorithm/settings | Matches |
| Dense depth | ordered included photos; engine compatibility; depth algorithm/settings | Alignment |
| Surface | coordinate convention; engine compatibility; surface algorithm/settings | Dense depth |
| Texture | ordered included photos; calibration; coordinate convention; engine compatibility; texture settings | Surface |
| LOD | coordinate convention; engine compatibility; LOD settings | Surface |
| Export | coordinate convention; engine compatibility; export settings | explicitly selected completed source stages, normally Texture and LOD |

Consequences verified by tests:

- photo include/exclude/reorder, original bytes, or capture metadata invalidate Features and every descendant;
- calibration or coordinate changes leave Features/Matches reusable but invalidate Alignment and every descendant;
- texture-only changes invalidate Texture and dependent Export, not Alignment/Dense/Surface/LOD;
- LOD-only changes invalidate LOD and dependent Export;
- export-only changes invalidate Export only;
- a different project revision/job attempt can have the same content identity, but cannot reuse or publish a manifest/checkpoint until its exact `ArtifactBinding` is admitted by the job/publication layer.

## Coordinate and representation contract

The current identifier must describe the repository convention without claiming metric scale: x-right, y-down, z-forward; row-major world-to-camera poses; arbitrary scale. Agent 031 owns the final pixel-centre and coordinate wording. Any semantic change must change the coordinate-convention identifier and invalidate affected geometry. Agent 061 owns export-space conversion and winding.

Representations are explicit. Sparse point clouds, dense depth/points, triangle meshes, texture atlases, textured meshes, LOD sets, and export packages cannot be substituted for one another. A manifest rejects a representation that does not belong to its stage.

## Existing M18 depth checkpoint compatibility

`DepthCheckpointIdentity` retains the exact M18 domain bytes and fingerprint ordering. Its default output is bit-for-bit identical to the audited implementation. It now names compatibility as schema 18 plus the exact algorithm domain and rejects unknown compatibility values. The directory remains `.depth-checkpoints-m18`; this change does not reinterpret native `ref-N.bin` files.

Agent 050 owns any successor native depth binary. A successor must introduce a new explicit compatibility value and reader or reject the old/new format; it must not relabel M18 bytes. Dense reuse must also be represented by a C8 `DENSE_DEPTH` manifest tied to binding, alignment parent, actual byte hashes, and independent numerical evidence.

## Publication and recovery protocol

Agent 009 does not own filesystem publication. Required integration order is:

1. compute/write artifact bytes to an attempt-private staging area;
2. validate representation-specific acceptance and build the manifest;
3. fsync files/directories as supported;
4. Agent 023 atomically publishes the artifact set and manifest **last**, after checking current project revision and job attempt;
5. readers decode and validate the manifest plus actual artifact probes before reuse;
6. Agent 020 garbage-collects only artifacts not reachable from current/last-completed manifests and not leased by an active attempt.

A partial, failed, cancelled, stale, unknown-version, or rejected stage never becomes current merely because files exist.

## Verification supplied on the Agent 009 branch

Focused JVM regressions cover canonical round trips, every relevant independent invalidation, stale binding, parent mismatch, representation mismatch, malicious lengths, malformed versions, bad hashes, traversal, streaming file replacement, exact sparse geometry restore, valid-checksum/invalid-geometry rejection, and every truncation boundary of representative manifests/checkpoints. Randomized tests compare the revised M18 fingerprint with an independent copy of the audited byte algorithm.

Physical-device process-death, power-loss durability, native dense numerical equivalence, and combined application wiring remain integration/device gates; they are not inferred from these pure contract tests.

## Receiving009 sparse-frontier intermediate byte store

`SparseFrontierCheckpointStore(privateProjectDirectory: File, byteBudget: Long =
26_000_224)` is the narrow receiving dependency for actual039 orchestration.
Supply the existing canonical private project directory (`directory.canonicalFile`).
The store uses only its child `sparse-frontier-checkpoints-v1`; it does not publish
project result metadata. Public calls are:

- `load(stageSha256: String, cancelled: () -> Boolean): ByteArray?`
- `publish(stageSha256: String, payload: ByteArray, cancelled: () -> Boolean): Boolean`

The exact64lowerhex canonical SPARSE identity binds an envelope containing
RFFRNT01 magic, big-endian version1, identity64ASCII, payload length and SHA256
of the actual written payload. Header112bytes, payload1..13_000_000bytes.
Length, exact file size, version and identity are checked before payload allocation;
SHA256 and final descriptor size are checked before accepting loaded bytes.039
still decodes/validates geometry, input ordering, anchors and stable source IDs.
A valid byte checksum is not accepted sparse geometry.

The constructor's explicit byte budget is113..26_000_224bytes. Publishing retains
at most two exact `64lowerhex.frontier` regular files. Admission counts retained
records plus the incoming temporary; bounded1024-entry scanning and exact-name
oldest-record eviction preserve originals, models, unknown names and symlinks.
Oversized exact-owned records are invalid and may be removed to admit recomputation.
Under the writer lease, only exact owned UUID temporary names are orphan-cleaned.
The `.frontier-store-v1.lock` inode is stable and never unlinked by this store.

Publication acquires a cross-process FileChannel writer lease with at most25
nonblocking attempts separated by10ms checks. It writes one unique CREATE_NEW
non-symbolic temporary, hashes the copied64KiB chunks actually written, completes
the checksum field, forces the file, atomically renames, and forces the directory.
Creating the cache directory also forces its project parent. Unsupported atomic
rename/directory sync and cache I/O errors return false or a cache miss; there is
no weaker rename/durability fallback. A failed directory sync may occur after a
complete atomic rename, so false never promises the validated cache file is absent.
No checkpoint intermediate is a completed project publication.

Cancellation callback true or thread interruption propagates CancellationException,
including from cache failure handling; it is never downgraded to a miss. Checks
bracket64KiB I/O and commit boundaries. Real storage/fsync latency and power-loss
behavior remain Android/device qualification, not host durability claims.

Receiving JVM tests use real temporary files, SHA/version/identity/length corruption,
symlinks, an actual nonempty-target atomic-rename failure, read/write cancellation,
byte admission, orphan cleanup, oversized records and an actual overlapping writer
lease. Host K2JVMCompiler2.1.21-Werror and JDK17 JUnit4 ran6tests successfully.
