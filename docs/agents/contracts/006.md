# C6 project access and reservation contract — Agent 006

Version: `c6-v2`
Campaign base: `ad3029193f304c70931b94ea7a0df90b69d84b07`
Initial implementation: `ba842ef5e22b58929426b6b39056ac15743f0fdb`

## Purpose

`ProjectRepository` is the compatibility façade for project identity, canonical private paths,
operation conflict policy, immutable input snapshots and validated current-result access. It no
longer owns the implementation of every storage operation. The default adapters are exposed as
focused `ProjectStorageServices` and can be replaced by the semantic owners without creating a
second repository or bypassing C6.

## Identity and request fields

`ProjectOperationRequest` is immutable and contains:

- canonical lowercase UUID `projectId`;
- canonical lowercase UUID `operationId`, allocated before suspension;
- `ProjectOperationKind` and its declared `SHARED`/`EXCLUSIVE` access mode;
- optional non-negative `expectedRevision`;
- `ProjectJobIdentity(jobId, attemptToken)` for `RECONSTRUCT` and `PUBLISH_RESULT`.

Both job fields are canonical UUIDs. A reconstruction/publication request without a durable job
attempt is rejected before reservation acquisition. M19 DAO state/completion calls remain through
explicitly named `LEGACY_*` compatibility kinds until owners 001/002/007/023 wire durable jobs.

## Conflict policy

- Shared current-result/input reads and capture/result exports may coexist in one process.
- Input/capture mutation, project commands, cleanup, deletion, reconstruction, publication and
  project-file writes are exclusive per project.
- Operations on different projects are independent.
- A duplicate `operationId` is rejected rather than treated as reentrant work.
- The store holds an OS file lock under `files/projects/.project-access/<projectId>.lock`. The OS
  releases it on process death. Receipt content is diagnostic and is replaced after recovery; it
  is not accepted as proof that a dead owner still holds a lease.
- Other processes are conservatively excluded even for shared reads. This sacrifices cross-process
  read concurrency to prevent partial-project exposure.

`withProjectAccess` obtains the reservation first, verifies existence/revision, invokes the block,
and rechecks stable-revision operations before releasing in `NonCancellable` cleanup.

## Lease-bound reads

A caller that already owns a C6 reservation must not call a convenience read that acquires another
reservation. In particular, `RECONSTRUCT` is exclusive, so nesting `inputSnapshot(projectId)` inside
it would conflict with itself. C6 v2 therefore exposes:

- `inputSnapshot(session)` for immutable input identity under the active reservation;
- `currentResult(session)` for validated current-result identity under the active reservation.

The session is a repository-bound capability. It is created only by `withProjectAccess`, is rejected
by another repository instance, and is invalid immediately after the block exits. Session-bound
reads require an operation kind whose `stableRevisionRequired` flag is true and revalidate the
acquired revision around the read.

The project-ID convenience overloads remain for standalone reads and acquire/release their own
`READ_INPUTS` or `READ_CURRENT_RESULT` reservation.

## Path and artifact policy

- Project, photo, operation, job and attempt IDs use canonical UUID text.
- Every project path is normalized/canonicalized below `files/projects/<projectId>`.
- Existing symbolic-link components, traversal-like names and external files are rejected.
- Original filenames must be exactly `<photoId>.image` and match the stored photo ID.
- Artifact keys remain `sparse-(?:mNN-)?r<revision>-<16 lowercase hex>` and are checked against
  the project revision before current-result access/publication.
- Supported M19 artifact extensions remain JSON, GLB, PLY, dense GLB/PLY, mesh GLB/PLY,
  photographic GLB and texture PNG.

## Published interfaces

- `ProjectAccess.inputSnapshot(projectId)` is the standalone immutable snapshot convenience call.
- `ProjectAccess.inputSnapshot(session)` reads the same snapshot without nesting a lease.
- `ProjectAccess.currentResult(projectId)` is the standalone validated-result convenience call.
- `ProjectAccess.currentResult(session)` reads the result inside an existing reservation.
- `ProjectAccess.withProjectAccess(request, block)` is the integration point for long-lived
  reconstruction, export, publication and deletion flows.
- `ProjectStorageServices` has one provider each for create, photo import, preview reopening,
  capture archive, deletion and atomic project-file writes.
- `ProjectRepository.dao` is a compatibility adapter. Direct mutations participate in reservations,
  but new code must use C6 requests so durable job identity spans the full operation rather than a
  single DAO statement.

## Required caller pattern

```kotlin
val request = ProjectOperationRequest(
    projectId = boundProjectId,
    operationId = boundOperationId,
    kind = ProjectOperationKind.RECONSTRUCT,
    expectedRevision = boundRevision,
    job = ProjectJobIdentity(jobId, attemptToken),
)
repository.withProjectAccess(request) { session ->
    val snapshot = repository.inputSnapshot(session)
    pipeline.run(snapshot)
}
```

Do not infer project ID/revision after an activity result returns. Do not retain a session or `File`
returned by legacy helpers and assume it remains current after the reservation closes. Open, copy
and validate current artifacts inside the active `withProjectAccess` block, using the session-bound
read overloads when the operation already owns a lease.

## Known integration limits

- The current M19 `ScannerViewModel` and `SparsePipeline` still perform several direct DAO reads and
  do not yet hold one durable reconstruction lease for their complete lifetime. Revision checks and
  coordinated mutation/publication adapters prevent stale completion, but owners 001/002/007/023
  must wire the full request before final resilience acceptance.
- Deletion now refuses symlink escape and does not follow links, but durable tombstone/journal
  recovery remains owner 022. Atomic writes fsync file contents and rename on the same filesystem;
  owner 023 owns full publication manifests and power-loss evidence.
- SAF destination rollback/cleanup remains owner 026. C6 prevents conflicting private-project
  changes but cannot make an arbitrary document provider transactional.
- Multi-project commands such as independent duplication need a deterministic multi-project lock
  order agreed with owner 019 before implementation; C6 v2 exposes one project per request.
- Emulator/device process-death, storage-fault and physical ARM64 gates remain separate evidence;
  a successful host/Android compile does not close them.
