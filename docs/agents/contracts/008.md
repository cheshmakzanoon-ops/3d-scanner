# C7: durable Android execution and platform lifecycle

Verified against official Android documentation on 2026-10-20. This document records
the implemented policy and the device gates still required; reading the policy is
not evidence that the foreground service has passed those gates.

## Execution choice

A visible user action starts `ReconstructionService` directly. The application-owned
`ReconstructionExecutionController` obtains a `RoomJobStore` lease and executes the
bounded local pipeline. Room job records describe application work; they do not
schedule Android `JobScheduler` jobs. Android's documentation explains that foreground
WorkManager tasks still consume job quota on Android 16 and describes direct service
launch as an option for this situation. [Long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)

| Platform | Foreground type selected at runtime | Reason and constraints |
| --- | --- | --- |
| API 29–34 | `dataSync` | Android lists local file processing among this type's uses. The manifest declares its foreground permissions. |
| API 35–36 | `mediaProcessing` | The job processes existing photographic assets into derived local media. This is the implementation's application of Android's documented media-processing category; it is not a claim of Play review approval. |

Android 14 and later require the appropriate declared foreground-service type and
its permission. Camera access stays with the visible CameraX lifecycle; CPU work
does not claim the camera service type. The service type depends on the OS version
and never changes to gain additional time after a quota is exhausted.
[Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types)

For apps targeting Android 15+, the background budget for `dataSync` and
`mediaProcessing` is six hours in a rolling 24-hour period, tracked separately by
type across the application's services. `onTimeout(startId, fgsType)` requests native
cancellation, stops foreground promotion and calls `stopSelf()` immediately. It does
not wait for a long native stage or filesystem cleanup in that callback.
[Foreground service timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout)

## Admission, control and restart

The service returns `START_NOT_STICKY`. There is no boot receiver. A new job or an
explicit resume action is required to start expensive work; opening the application
reconciles old work and leaves it resumable. Android normally restricts background
foreground-service starts on API 31+, with documented exceptions for user actions
such as notification interaction. A rejected start leaves the saved job paused and
reports that the user should reopen and resume it.
[Background start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

The service promotes its initial notification before suspending for Room recovery.
Posting permission is handled separately from mandatory foreground promotion:
Android does not require `POST_NOTIFICATIONS` to launch an FGS, but still requires
the notification supplied to `startForeground`. Permission denial can hide its
drawer entry, so the application retains pause/resume/cancel controls and explains
the permission state. Processing uses a private lock-screen notification and the
actual persisted job/attempt identity. [Notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

| Event | Implemented transition |
| --- | --- |
| Repeated Start / Resume | The service drain binds one worker; the controller admits work through one durable lease and waits for the previous worker to release native state. |
| Rotation, selecting another project, activity background | CPU work remains owned by the application/service. UI selection does not replace its project, revision, operation or attempt identity. Camera lifecycle remains separate. |
| Screen off / OS suspension | Accepted checkpoints remain durable. If suspension prevents a lease renewal, the expired attempt cannot publish; reopening offers validated recovery. Continuous execution is not guaranteed. |
| Pause / Cancel action | The action URI and extras must match the current job, revision and attempt. The durable command is recorded before cancelling the corresponding native token. |
| Task removal / service timeout | Request interruption, remove foreground state, stop the service, and leave recovery to the ledger. |
| Process kill / user Stop / force-stop | No callback is assumed. On reopening, expired work is reconciled and requires explicit resume; partial files never become the current result. |
| Completed, failed or paused work | The foreground service drains and stops. Owner 029 reconciles separately tagged result/pause notifications from Room. |

Android's Task Manager Stop action removes the app from memory without callbacks.
The platform supplies an `ApplicationExitInfo` reason when the app later restarts;
the checkpoint protocol does not depend on receiving the stop callback.
[User-initiated stopping](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)

## Durable boundaries

Every admitted job fixes original/selection, calibration, settings, engine and
resource-plan identities. A synced C8 input record or stage manifest exists before
Room acknowledges its hash. Recovery verifies the complete parent/file closure and
independently validates sparse geometry. A new attempt explicitly rebinds reusable
content and can reset its own stage counters. Rejected or corrupt checkpoints restart
from originals without deleting the last completed result.

Result publication verifies the current revision and exact operation/attempt. Files,
current/previous result pointers, immutable receipt and job completion form one
journaled publication operation. A late, cancelled, expired or superseded worker
cannot advance the current pointer.

Resource admission consumes the job's fixed owner-030 plan. Thermal, managed/native
memory and measured storage checks run at safe checkpoints and outside the atomic
publication section. Operational resource/cancellation errors propagate through
optional geometry stages. Missing camera/geometry/texture evidence is never filled
with fabricated success.

## Required verification still to execute

The real, supplied lifecycle harness can be invoked with:

```bash
./gradlew :app:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.realityforge.scanner.agents.a008.ReconstructionServiceLifecycleDeviceTest
```

It starts work through the actual Activity/ViewModel and waits for measured production
pipeline progress, then exercises activity recreation/backgrounding, repeated Start,
malformed commands, actual `finishAndRemoveTask`, and foreground-service drain/stop.
It checks original hashes, immutable job inputs, one acquired attempt and valid result
publication. It supplies no fake service, stub pipeline or artificial native lifetime.
The fixture photographs are labeled synthetic. Its current receipt is **NOT_RUN**.

`MainActivity.onStop` still calls the host hook, but the ViewModel hook is now a no-op
for CPU work. The activity-stop cancellation behavior has therefore already changed;
the hook's existence is not evidence that the old policy is retained. Agent 001's
explicit lifecycle acceptance gate remains pending until this actual runner harness
and the required matrix pass.

Run the integrated Android build, instrumentation and compatibility matrix against
the final source revision. Cover API 29, 33, 34, 35 and 36; permission granted and
denied; rotation/background/screen-off; rejected background start; repeated and stale
notification actions; task removal; configured short timeout; process kill; and
force-stop followed by explicit reopen/resume. Retain the actual job records, current
and previous artifact identities, and native release-latency measurements.

Host JNI syntax checks, pure state-machine tests and notification intent fixtures do
not establish platform lifecycle behavior. No physical-device latency, thermal
duration, minified ABI load or uninterrupted-background guarantee is claimed here.

For API 35/36 timeout trials, use the official short-timeout testing instructions on
the foreground-service timeout page linked above in a dedicated emulator/fixture.
Record and restore any changed test-only device configuration. An external controller
must observe timeout/Stop/process-kill/force-stop cases because killing the application
also kills instrumentation hosted in its process. Reopen the app explicitly, record the
new attempt and accepted checkpoint identities, and compare original/current/previous
artifact hashes before accepting recovery. A direct call to `onTimeout` on an unattached
service does not substitute for this platform test.
