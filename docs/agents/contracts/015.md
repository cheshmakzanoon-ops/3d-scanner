# Agent 015 camera optical-control contract

Branch: `agents/015-camera-optical-controls`

This contract is intentionally outside `CameraScreen.kt`, database entities, diagnostics schemas,
and navigation ownership. It exposes bounded types/adapters for Agents 014, 013, and 010.

## Public capture-control surface

Package: `com.realityforge.scanner.capture.controls`

- `CameraCapabilities` is the truthful interpreted capability snapshot. Unsupported or missing
  Camera2 keys remain unavailable; no control is inferred from a device category or lens label.
- `OpticalControlRequest` binds every command to `CaptureSessionToken`, `OpticalCommandId`, and
  an exact `CameraIdentity` (logical plus optional physical ID).
- `CameraOpticsController` serializes commands, publishes `AppliedOpticsState`, applies a bounded
  timeout, and rejects completions after rebind/unbind. `ACKNOWLEDGED_UNCONFIRMED` is distinct
  from `APPLIED`.
- `CameraOpticsUiModelFactory` produces a platform-neutral Compose-ready model without owning
  strings, navigation, or `CameraScreen`.
- `AppliedOpticsMetadata` carries the result-confirmed logical/physical camera, focal length,
  zoom, crop, exposure time, ISO, aperture, focus distance, AE/AWB lock state, sensor timestamp,
  and frame number.

## Agent 014 integration sequence

1. Select a logical `CameraInfo`; call `CameraXCapabilityReader.read` before use-case binding.
2. Keep one immutable capture session token and exact selected physical camera ID for the
   session. Do not change either between shots.
3. Construct `Camera2CaptureResultObserver` with that identity and active array.
4. Before building use cases, call `CameraXOpticsInterop.configurePreview` and
   `configureImageCapture` with the same physical ID. CameraX must not receive mixed physical
   IDs in one binding.
5. After binding, construct `CameraXOpticsBackend` from the returned `Camera`, capabilities,
   observer, and a preview-specific `CameraMeteringPointProvider`.
6. Call `controller.bind(...)`. Collect `controller.state`; render
   `CameraOpticsUiModelFactory.create(capabilities, state)`.
7. On permission loss, lifecycle disposal, project/session replacement, or failed rebind, call
   `controller.unbind(reason)` before dropping the CameraX binding.
8. Do not display AE/AWB as locked for `PENDING` or `ACKNOWLEDGED_UNCONFIRMED`; only `APPLIED`
   represents matching Camera2 capture-result evidence.

## Agent 013 metadata handoff

Map `AppliedOpticsMetadata` into the canonical immutable capture metadata record. Preserve null
for unavailable values. `activePhysicalCameraId` and result-confirmed focal/zoom/crop values must
remain distinct from user intent. Do not write CameraX/Camera2 classes into persistence.

A still-image callback should snapshot the newest observer metadata associated with that capture
session. A result from a different logical camera or a changed physical ID is a failure, not a
valid photo metadata fallback.

- `OPTICS_PHYSICAL_CAMERA_CHANGED`

Agent 010 may map these codes into its typed failure schema; Agent 015 does not localize them.

## Device-specific fallbacks

- Missing AF regions: focus metering is unavailable; capture remains possible.
- Missing exposure-compensation range: the slider is unavailable.
- Missing AE/AWB lock characteristic: the corresponding lock is unavailable.
- CameraX control future completes but no matching result arrives: state remains
  `ACKNOWLEDGED_UNCONFIRMED`.
- Missing active physical ID in capture results: metadata remains unknown; a conflicting ID is
  never substituted.
- Camera-control failure: report the typed failure and preserve normal capture/import fallback.
